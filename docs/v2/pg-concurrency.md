# 从 SQLite 换到 PostgreSQL：并发写入的问题和对照数字

## 问题

SQLite 同一时刻只有一个写入方。动作网关用 `BEGIN IMMEDIATE` 先拿到整库写锁，“读状态 → Guard 判定 → 写入”这一段不会被别的请求插进来。

换到 PostgreSQL 后，多个请求可以同时读到同一份状态，各自判定，然后同时写。同一笔退货被同时批准，或者同一个请求被重复提交，都会撞在一起。

## 解决办法（PR #49）

1. **行锁。** 动作开始时，先锁住它要操作的订单和订单项（`FOR UPDATE`），Guard 读到的其余行（物流、售后单、工单等）加 `FOR SHARE`；换货的目标库存行要被扣减，所以加 `FOR UPDATE`（阶段 C）；审批和执行时，还要锁住待审批记录。同一订单、同一笔待审批的请求排队执行，不同订单之间互不影响。
2. **固定加锁顺序**：订单 → 订单项 → 待审批记录 → 其余行。所有请求都按这个顺序加锁，就不会出现互相等待（死锁）。
3. **幂等键 + 唯一约束兜底。** 同一个请求总会算出同一个幂等键，待审批表和回执表都对它建了唯一约束；一个订单项同时只能有一张进行中的售后单、工单或待审批。排在后面的请求会读到前一个已经提交的结果，直接作为重放返回。

## 对照数字

在 PostgreSQL 16 上跑 3 个场景，每个场景 20 轮，每轮 20 个线程同时发起；每轮用一个新建的数据库 schema。“去锁”是指脚本运行期间把三个加锁函数临时换成空操作，磁盘上的代码不变。

| 场景 | 去锁 | 加锁 |
|---|---|---|
| 同一笔待审批退货，20 个线程同时批准 | 20/20 轮都只执行 1 次、1 条回执，但每轮有 18–19 个调用方被告知“失败”（共 379/400），动作其实已经执行 | 20/20 轮只执行 1 次；400/400 个调用方都得到“已执行”（其中 380 次为重放） |
| 同一个幂等键的动作，20 个线程同时提交 | 20/20 轮都只落库 1 条工单、1 条回执，但每轮有 19 个调用方被告知失败或被拒（共 369 次失败、11 次拒绝），审计里每轮还多出 8–19 条“未执行” | 20/20 轮只落库 1 条；400/400 个调用方得到“已执行”，审计里 0 条“未执行” |
| 同一 SKU（库存 5），20 个换货同时申请（阶段 C 修复前） | 20/20 轮 20 个全部通过，超出库存 15 件；最终库存仍是 5 | 与去锁完全相同 |
| 同上（阶段 C：执行换货时扣减库存） | 20/20 轮只接受 1 个，没有超卖，但还剩 4 件时就有 19 个请求被告知“库存不足” | 20/20 轮正好接受 5 个，超卖 0，最终库存 0；其余 15 个得到“库存不足” |

## 怎么理解这些数字

- **去锁后没有出现重复执行。** 唯一约束和版本号校验是第二道防线，挡住了第二次写入。去锁的问题在于结果报错：动作已经执行了，每轮却有 18–19 个调用方被告知失败，同一幂等键的场景里审计也记下了“未执行”。前端会显示失败，操作员可能会再处理一遍。加锁后，后来的请求排队等待，读到已提交的结果，返回“已执行（重放）”。
- **11 次“拒绝”。** 这些请求查幂等记录时，第一个请求还没提交；等到 Guard 读数据时，第一个请求已经提交了，于是读到了刚建好的工单。同一个事务里两次读到了不同的状态。加锁后，同一订单的请求串行执行，这种情况不再出现。
- **换货超卖：先补扣减，再靠锁。** 阶段 B 时，Guard 只检查“库存 ≥ 数量”，换货不扣减库存，所以两种模式下 20 个请求都能通过，这不是锁能解决的问题。阶段 C 改为执行换货时用一条带条件的 UPDATE 扣减库存（只在产品运行时生效，见 [exchange-stock-deduction.md](exchange-stock-deduction.md)）。改完之后：
  - 去锁时不再超卖，但所有请求读到的是同一个版本号，条件 UPDATE 只有第一个能成功，其余 19 个都被拒，库存还剩 4 件。
  - 加锁时，目标库存行加 `FOR UPDATE`，同一 SKU 的换货依次排队，每个请求都能读到最新库存：正好接受 5 个，库存扣到 0。

## 复现

```powershell
docker compose up -d --wait
.\.venv\Scripts\python.exe -X utf8 scripts\pg_concurrency_compare.py `
    --url postgresql://aftersales:aftersales-dev@127.0.0.1:55432/aftersales `
    --out docs\v2\pg-concurrency-results.json
```

每一轮的明细在 `docs/v2/pg-concurrency-results.json`，脚本自动生成的表格在 `docs/v2/pg-concurrency-results.md`。阶段 B 用 20 轮 × 20 线程、PostgreSQL 16.15、Python 3.12 跑完 3 个场景，用时约 107 秒。阶段 C 只用 `--scenarios same_sku` 重跑了场景 3，用时约 77 秒；另外两个场景不经过换货代码，结果沿用阶段 B 的数据，阶段 B 的场景 3 数据保存在 JSON 的 `superseded` 字段里。
